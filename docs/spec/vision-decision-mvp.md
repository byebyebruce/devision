# Spec：视觉决策模型 MVP（"能看图的 Jev"）

> 状态：ready-for-agent · 日期：2026-09-30
> 背景调研：`../research/jev-api.md`、`../research/encoder-data.md`

## Problem Statement

我想要一个"System One"式的视觉决策模型：给一张图和若干个简单的英文问题（如"图里有没有狗？""图里的人是站着还是坐着？"），直接返回结构化的决策结果和校准过的概率，而不是生成一段文本。

现有方案都不满足：

- **Jev**（TypeSafe AI）只接受文本输入，官方文档明确写着不支持图像、音频、视频；而且它是闭源托管 API，只能远程调用。
- **Laya**（Jev 的开源对应物）同样只处理文本。
- **通用 VLM** 输出自由文本，要自己解析；没有校准过的概率；在服务器 CPU 上跑得太慢。
- **laya-vision**（社区 fork）最接近这个需求，但视觉部分绑定在 SmolVLM 上，训练流程绑定在 Modal 平台上，没法按我的选型替换视觉编码器，也没法在本地训练。

## Solution

自建一个视觉决策模型，对外接口和 Jev 的 `/v1/systemone` 协议兼容：

- 请求的 `state` 可以放图片；问题和答案的结构与 Jev 完全一致。
- 模型的组成：
  - SigLIP2-B/16-256 负责视觉编码，参数冻结；
  - 视觉特征经过投影层，送进用 Laya 权重初始化的 ModernBERT-large；
  - 每个候选选项在它对应的 `[MASK]` 位置打分。
- 训练在 1 张 A100 上完成；推理跑在服务器 CPU 上。
- MVP 的目标是**端到端跑通**：
  - 用规则把少量 GQA 和 VQAv2 数据转换成决策题；
  - 训练；
  - 通过 `decide` 接口和 HTTP 服务回答问题；
  - 评测准确率、ECE 和 CPU 延迟，并和 laya-vision 对比。

本项目仅限非商业用途。

## User Stories

### 调用方（API 使用者）

1. 作为调用方，我想在一个请求里传一张图和多个问题，然后一次拿到所有答案，这样就不用为每个问题单独请求一次。
2. 作为调用方，我想用和 Jev 一样的请求结构（`state`、`model`、`questions`），这样现有的 Jev 客户端代码几乎不用改。
3. 作为调用方，我想把图片作为 `state` 数组中的一个片段传进去，这样同一个请求里还能附带文字上下文。
4. 作为调用方，我想用 base64 或 URL 两种方式传图片，这样本地图片和远程图片都能处理。
5. 作为调用方，我想发纯文本请求（不带图）时也能拿到合法的响应，这样能和 Jev/laya-serve 的请求互换使用。
6. 作为调用方，我想问是/否类问题（`noul`），然后拿到"是"的概率，这样可以按自己设的阈值做判断。
7. 作为调用方，我想问多选一问题（`choice`），并且每次请求自己给出候选项，这样不用受限于固定的类别集合。
8. 作为调用方，我想让 `choice` 候选项的描述可以留空（null），这样简单的选项只写名字就行。
9. 作为调用方，我想拿到 `choice` 每个候选项的概率，并且所有概率加起来等于 1，这样可以做 top-k 或者自定义决策。
10. 作为调用方，我想拿到 `confidence`，并且它的计算方式和 Jev 相同（`(n·p_max−1)/(n−1)`），这样在 Jev 上调好的阈值能直接用。
11. 作为调用方，我想给问题附加 `instructions`，也就是额外的判断标准，这样可以细化判断规则。
12. 作为调用方，我想让问题 ID 由我自己命名，并且 ID 不影响模型的判断，这样命名不会带来副作用。
13. 作为调用方，我想在响应里看到 `model` 版本号和 `usage`，这样方便排查问题和做统计。
14. 作为调用方，我想在请求不合法时拿到 422 和清楚的错误信息，比如题型未知、选项少于 2 个、图片无法解码，这样能快速定位问题。
15. 作为调用方，我想让任意尺寸、任意长宽比的图片都能被处理（包括长图），这样不用自己做预处理。
16. 作为调用方，我想让同一个请求得到确定的结果，这样结果能复现、能缓存。
17. 作为调用方，我想让服务在服务器 CPU 上的 P50 延迟低于 300ms，这样能放进在线流程里。

### 训练者（ML 工程师，也就是我）

18. 作为训练者，我想用规则把 GQA 中的 verify 题转成 `noul`，把 choose 题转成两个选项的 `choice`，这样不用调用 LLM 就能生成数据。
19. 作为训练者，我想用规则把 VQAv2 的 yes/no 题转成 `noul`，这样能直接利用它平衡过的是/否分布。
20. 作为训练者，我想把转换后的数据存成 JSONL，并且格式和 Jev 请求一致（再加上标准答案），这样训练、评测、线上服务共用同一种格式。
21. 作为训练者，我想让每条样本都记录来源数据集和图片 id，这样能去重，出问题时也能追溯。
22. 作为训练者，我想按图片 id 把评测集用到的图片从所有训练源中剔除，这样可以避免 COCO/VG 图片在不同数据集之间泄漏。
23. 作为训练者，我想用一个参数指定每个数据集取多少条，这样可以先用几十或几百条跑通流程，再扩到 1 万条。
24. 作为训练者，我想让数据转换的结果在固定随机种子下可复现，这样实验可以对比。
25. 作为训练者，我想用 Laya 官方的 checkpoint 初始化 ModernBERT-large，这样模型一开始就懂 `noul` 和 `choice` 的决策格式。
26. 作为训练者，我想冻结 SigLIP2，只训练投影层和决策头，并给 ModernBERT 加 LoRA，这样在 1 张 A100 上能快速迭代。
27. 作为训练者，我想让训练目标沿用 Laya 官方的 RLCD，这样和 Laya 的概率语义一致。
28. 作为训练者，我想在训练结束后做温度校准，这样输出的概率不会过度自信。
29. 作为训练者，我想用一个配置切换视觉 token 的数量（64 个，或者 256 个即不压缩），这样可以做消融实验。
30. 作为训练者，我想通过配置替换视觉编码器，比如以后换成 So400m，这样后续做编码器对比时不用改代码。
31. 作为训练者，我想在训练中看到 loss 和 val 准确率，这样能及时发现训练发散。
32. 作为训练者，我想让 checkpoint 保存下来以后，能直接被 `decide` 加载，这样训练和服务之间不需要额外的转换步骤。
33. 作为训练者，我想用一条命令完成"转换少量数据 → 训练若干步 → 调用 decide"的冒烟测试，这样每次改动后都能快速验证整条流程。

### 评测者

34. 作为评测者，我想在留出的 val 集上看 `noul` 和 `choice` 的准确率，这样可以衡量模型质量。
35. 作为评测者，我想看 ECE（校准误差），这样可以衡量概率是否可信。
36. 作为评测者，我想在 POPE 上评测"有没有某物"类问题，这样可以和公开结果横向对比，也能检测模型是否会凭空"看到"不存在的物体。
37. 作为评测者，我想在同一个测试集上跑 laya-vision baseline，这样能判断我们的架构是否更好。
38. 作为评测者，我想在服务器 CPU 上测 `decide` 的 P50 和 P95 延迟，这样可以验证是否满足部署约束。
39. 作为评测者，我想让评测只通过 `decide` 接口进行，这样评测到的就是线上真实会执行的代码路径。
40. 作为评测者，我想把评测结果输出成结构化文件，这样不同实验之间可以对比。

### 运维者

41. 作为运维者，我想用一条命令启动 HTTP 服务，并暴露 `/v1/systemone`，这样可以直接部署。
42. 作为运维者，我想让模型在服务启动时只加载一次，这样请求不会重复承担加载开销。
43. 作为运维者，我想让服务在没有 GPU 的机器上正常运行，这样可以部署到 CPU 服务器。

## Implementation Decisions

### 模块

- **图像预处理**
  - 接收任意尺寸的图片；保持长宽比缩放，然后补边到 256×256（letterbox），再做 SigLIP2 的归一化。
  - 训练和推理用同一个实现。
- **视觉分支**
  - SigLIP2-B/16-256 输出 256 个 patch token，参数冻结。
  - 做 2×2 pixel shuffle，压到 64 个 token。token 数量可以配置，设为 256 时就是不压缩。
  - 最后经过一个 MLP 投影层，映射到 ModernBERT-large 的隐藏维度。
- **决策编码器**
  - ModernBERT-large，用 Laya 官方的 checkpoint 初始化。
  - 输入序列由三部分组成：视觉 token（放在最前面）、state 中的文本、问题和选项。
  - 输出头与 Laya 一致：每个选项或每个是/否位置对应一个 `[MASK]`，先在这些位置打分，再做 softmax。
  - 训练时 ModernBERT 加 LoRA；投影层和决策头做全量训练。
- **`decide`（深模块，唯一的主 seam）**
  - 输入和输出都是 Jev 格式的 `state` 和 `questions`。
  - 内部完成请求校验、图片解码与预处理、编码、打分、温度校准，最后按 Jev 的格式组装答案。
  - HTTP 服务和评测都只调用它。
- **数据转换器**
  - 纯函数：输入一条原始数据集记录，输出零条或多条 Jev 格式的样本，并附带标准答案。
  - MVP 阶段只实现 GQA（verify 转 `noul`，choose 转 `choice`）和 VQAv2（yes/no 转 `noul`）。
  - 可以借鉴 laya-vision 里 `cauldron.py` 的思路。
  - 规则如下：
    - 按图片 id 剔除评测集用到的图片；
    - VQAv2 成对取样，保证"是"和"否"的数量平衡；
    - 用固定的随机种子。
- **训练脚本**
  - 以 Laya 官方的 RLCD 训练脚本（Apache-2.0）为骨架，在上面加入视觉分支和图片数据加载。
  - 在 1 张 A100 上本地运行，不依赖 Modal。
  - 训练结束后在 val 集上拟合一个温度参数，和 checkpoint 一起保存。
- **HTTP 服务**
  - 对 `decide` 的薄封装，路由是 `POST /v1/systemone`。
  - 进程启动时加载模型，只跑在 CPU 上。
- **评测脚本**
  - 通过 `decide` 在 val 集和 POPE 上计算准确率、ECE、P50/P95 延迟，输出结构化结果。
  - 另外单独跑一次 laya-vision baseline 作为对照。

### API 契约

与 Jev 的差异只有一处：`state` 可以是数组，数组元素里可以有图片片段。其余请求字段和整个响应结构都与 Jev 相同。以下是数据形状（按 Jev 文档整理，图片片段是我们新增的）：

```
Request
  state: string | object | Array<string | object | ImagePart>
  ImagePart: { type: "image", base64?: string, url?: string }   // 二选一
  model: string
  questions: { [id]: Question }
  Question:
    { type: "noul",   question: string, instructions?: string, criteria?: string }
    { type: "choice", question: string, instructions?: string, criteria: { [option]: string | null } }  // 2..255 个选项

Response
  model: string
  answers: { [id]: Answer }
  Answer:
    noul:   { noul: number /* P(yes) ∈ [0,1] */ }
    choice: { choice: string, probabilities: { [option]: number /* 和为 1 */ }, confidence: number }
  usage: { input_tokens, output_tokens }
```

- MVP 阶段每个请求最多带 1 张图。
- `score` 题型会以 422 拒绝。
- `confidence = (n·p_max − 1)/(n − 1)`，其中 n 是选项数；这与 Jev 所有官方示例的数值都吻合。
- 错误码：422 表示请求不合法，500 表示内部错误。MVP 阶段不做鉴权和限流。

### 其他决定

- 只支持英文。只处理单张图片，不支持视频。
- 本项目仅限非商业用途，因此 GQA、COCO 图片以及 laya-vision 的 CC BY-NC-SA 权重都可以用作研究和 baseline。
- MVP 阶段的数据全部用规则生成，不调用 LLM。

## Testing Decisions

- **好测试的标准**：只测外部行为，也就是 Jev 格式的输入和输出，以及数据文件的内容。不测张量形状、层结构这类内部实现，这样换编码器或调整架构时测试不需要改。
- **主 seam `decide` 的测试**：
  - 纯文本请求和带图请求都返回合法响应，并且字段与 Jev 的 schema 一致。
  - `choice` 的 `probabilities` 键集合与请求中的候选项集合完全相同，概率和为 1（在误差允许范围内）；`choice` 字段是概率最大的那个选项；`confidence` 符合公式。
  - `noul` 的值在 [0,1] 之间。
  - 非正方形图片和极端长图都能正常处理。
  - 同一个输入重复调用，得到完全相同的输出。
  - 以下非法请求返回 422：题型未知、`score`、选项少于 2 个、图片无法解码、一个请求里有多张图。
  - 修改问题 ID，答案不变。
  - 为了让单测跑得快，可以用一个随机初始化的小模型替身来测上面这些契约，但必须走真实的 `decide` 代码路径。
- **数据转换器的测试**：
  - 用手写的几条 GQA 和 VQAv2 原始记录做输入，检查输出样本的题型、选项和标准答案是否正确。
  - 评测集里的图片 id 不会出现在输出中。
  - 固定随机种子时，输出完全相同。
- **端到端冒烟测试**：
  - 转换几十条数据，训练几十步，保存 checkpoint，然后用 `decide` 加载并回答问题。
  - 断言 loss 在下降，并且在训练样本上的准确率高于随机水平。
  - 这个测试只在有 GPU 的机器上手动运行，或者按需运行。
- HTTP 层不单独测试。
- **可参考的已有测试**：这个仓库目前是空的，没有已有测试可以参考。可以参考 laya-serve 的请求和响应示例，以及 `jev-api.md` 里整理的 Jev 官方示例，把它们作为 golden fixture。

## Out of Scope

- `score` 题型。
- GUI 截图和高分辨率输入（256×256 下看不清 GUI 里的文字）。
- 视频、多帧、一个请求里带多张图。
- 中文和其他语言。
- 用 LLM（如 Sonnet）生成干扰选项或改写问题。
- 其他数据集的转换，包括 Open Images、TallyQA、VSR；把数据扩到 1 万条及以上属于下一阶段。
- 全量微调 ModernBERT、解冻 SigLIP2、换用 So400m 或其他编码器做对比。
- 商业化授权相关工作。
- 鉴权、限流、批量接口、`/v1/models` 接口。
- int8 量化和 ONNX/OpenVINO 导出。只有当 CPU 延迟不达标时才考虑。

## Further Notes

- **风险 1：延迟。** ModernBERT-large 的输入是 64 个视觉 token 加上文本，在服务器 CPU 上能否做到 P50 < 300ms 还没有实测过。子代理在 M4 上测了结构相同的 ViT-B@256，编码大约 50–60ms。如果最后不达标，按以下顺序处理：先量化，再换 ModernBERT-base。
- **风险 2：Laya checkpoint 与视觉 token 的兼容性。** Laya 从来没见过视觉 token，投影层要从零学习对齐。数据只有几百到 1 万条时，效果可能有限，所以 MVP 阶段只要求流程跑通。
- **风险 3：视觉 token 压缩。** laya-vision 在 256px 下把 token 压到 16 个时，精细任务的效果崩了。我们压到 64 个，是调研建议的上限，需要用 256 个 token 的消融实验来验证。
- Laya 的 `confidence` 用的是基于熵的算法，和 Jev 不同。我们对外采用 Jev 的公式，所以直接拿 laya-serve 的阈值来用是不成立的。
- 本文档里的 Jev 协议细节来自 `jev-api.md`。文档中有两处没说清：请求里最多能放多少个问题；`instructions` 是否可以为 null。实现时按宽松的方式处理。
