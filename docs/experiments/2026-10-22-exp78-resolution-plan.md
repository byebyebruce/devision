# exp78：输入分辨率是不是瓶颈（256 vs 384，2026-10-22，运行前写下）

负责人 2026-10-22："可以，先做一吧"（方向 1：改结构，提升看得清的能力）。不算一轮，不产出可发布的模型。

## 背景

v0.4 的进步集中在专门造了数据的能力上；外部综合评测（MMBench +2.3、CV-Bench +0.7、NaturalBench +0.3、MME −0.6）几乎没动，抽查里数数、小物件（帽子）、小字（球衣号码）、示意图里的数字仍然错。这些都可能受 256×256 输入、64 个视觉 token 的限制。exp20（256 token）、exp38（512 输入）都只训了 2,000 步、数据很少，没有回答这个问题。

## 做法

- 起点都是 v0.4（`runs/r21-soft/train`）。384 臂只改 config：`image_size 384`、`interpolate_pos_encoding true`（SigLIP 位置编码双三次插值；`scripts/exp38/convert.py`，权重逐字节不变），24×24 patch 经 2×2 合并成 144 个视觉 token（256 臂 64 个）。
- **第 0 步（零训练）**：v0.4 直接按 256 / 384 / 512 读图，评开发集并测 CPU 延迟，只报告。
- **第 1 步（对照训练）**：两臂只差分辨率——同一份数据 `data/exp78/train.jsonl`（从 `data/n2/train_mix_fix.jsonl` 按固定种子随机取 160,000 题）、同一种子、20,000 步，r20 的设置（2e-5 / 1e-5 / 5e-5，SigLIP 顶 4 层 5e-6，预热 300），温度在 `data/v5/dev_mix.jsonl` 上拟合。

## 判定（只用开发集，同题配对，按图片重采样）

- **P1 细节面板**：`n2/dev_count`、`n2/dev_tallyqa`、`n2/dev_sqa` 的自然科学题、`n2/dev_v7w` 四个面板的题合在一起，384 − 256 的准确率差，下界 > 0 记为「分辨率有帮助」。
- **P2 不伤害**：`v5/dev_mix`、`n2/dev_spatial`、`v2/dev_coco_exist` 没有一个准确率差 ≤ −2 且上界 < 0。
- **报告**：CPU 单题延迟（4 线程，200 题，与 v0.4 的 289 ms 同一套测法）、每个面板分别的差值、训练速度和显存。

P1、P2 都满足：交负责人决定是否做完整的 384 一轮（含外部评测和 CPU 延迟取舍）。否则结论是「在这个预算下分辨率不是主要瓶颈」，转向方向 2（教师蒸馏）由负责人决定。
