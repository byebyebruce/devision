# EXP76 换设备前的预算重算与最小验证方案（EXP76-TIME-01、GPU-EVIDENCE-PREP-01 C；2026-10-20，只是方案，未运行）

背景：EXP76 两次 MPS 运行都在 d2 中途遇到 InnocentVictim GPU 错误（第一次在 step0 评测中，第二次在第 225–250 步之间），
两次都已按执行失败收尾（`runs/exp76-panel-decision*/report.json`）。评审裁决不放行第三次原样 MPS 重跑。本文写两件事：
一是按实测重算一次完整运行的时间；二是换设备或重启后、完整训练之前要先过的最小验证。
**训练配方不变**：R 起点、1,054 步的日程（学习率、预热、数据顺序）、数据、seed、精度（amp off）、监测集合都不动；
唯一的变量是设备和运行环境。本文不是运行许可：V 阶段和完整运行都要另行许可。

第 1 轮修订（GPU-EVIDENCE-R1-01 / R1-02）：
- V1 固定以第二次运行的完整 step0 为参照，8 题不豁免；MPS 概率容差 1e-6、预测必须一致；
- 运行时段内新出现的系统 GPU 事件计入 V 的结局；
- CUDA 的判据等资源明确后再预写；
- V 总上限 45 分钟，V2 在实际达到 250 次更新后按预定方式有界截停，V3 预留 300 s；
- 全量预算按上界 × 1.15 再加收尾余量重算，暂估 140 分钟。

## 1. 预算重算（EXP76-TIME-01）

我在第二次运行的回执里写的 ETA 有算术错误：剩余 829 步 × 3.3 s ≈ 46 分钟，从 04:30 算起已到 05:16，再加约 18 分钟终评就是 05:34，
超过了 05:32:09 的停止点，回执却写成「可以完成」。另外还漏算了一轮评测：`rlcd.py` 在 epoch 末先做一次 `run_eval`，
合并 LoRA 之后又对所有集合重新算一遍 `set_logits`。

一次完整 d2（第二次运行实测，MPS，Apple M4）：

| 部分 | 时间 | 依据 |
|---|---|---|
| 加载 + step0 监测（val、dev16、erased、k_text、4 个 rs_*） | 17.8 分钟 | 实测：阶段 03:59:42 开始，最后一个 step0 文件 04:17:29 |
| 训练 1,054 步 | 55.0–59.2 分钟 | 实测窗口 25–225 步，每步 3.13–3.37 s，按全程不变推算 |
| epoch 末 `run_eval`（同样 8 个集合） | 约 17.5 分钟 | 假设与 step0 的评测部分相同 |
| 合并后的 `set_logits`、拟合温度、写 final 明细 | 约 17.5 分钟 | 假设同上（前向过程相同） |
| 保存，流水线评测 exist（736 题）+ science（577 题） | 约 6.8 分钟 | 10-19 v04-k 上实测 4.3 + 2.0 分钟，另加保存约 0.5 分钟；模型不同，只作估计 |
| report_r2（不加载模型） | < 1 分钟 | 第二次运行实测 3 s |
| **合计** | **约 114–119 分钟** | |

- 守卫收尾的余量是 148 s：GRACE 15 + KILL_CHECK 5 + POLL 2 + 1 + 5，再加报告预留 120。只加这部分是约 116.5–121.5 分钟。
  上一版写的「121–126 分钟」不是这个算式，作废。
- **规则**：预算 = 各部分耗时的上界 × 1.15 + 148 s。按 119 分钟算：119 × 1.15 = 136.9，加 2.5 分钟 ≈ 139.3 分钟，
  **暂按 140 分钟（8,400 s）作方案估计**。
- V 阶段完成后，用实测各部分时间按同一规则锁定总上限，并在运行之前写进 runner；不能先运行再改截止。
- 原来的 5,700 s（95 分钟）**即使没有 GPU 错误也跑不完**：训练大约在第 75 分钟结束，紧接着的 epoch 末评测会被时限截断，
  结果是「到限、无结论」。
- 不删任何监测集合，不复用 step0，不把 epoch 末评测和合并后评测并成一轮（那要改公共训练实现）。如果要缩短监测，另行提出、另行裁决。

## 2. 同一台 Mac 重启后的最小验证（V 阶段，一次性，没有科学结论）

**总上限 2,700 s（45 分钟）**。各段时间：

- 最后 120 s 留给报告（不加载模型）；
- 报告之前留给 V3 300 s；
- V1 + V2 是同一个训练进程，必须在「总上限 − 120 − 300 − 28 s 守卫余量」= 2,252 s 之前结束。
  预估：step0 1,068 s，250 步 × 3.37 s = 843 s，合计约 1,911 s，余约 340 s。
- 这只是预估。实际变慢也**不延长**上限，到点就按「到限」结束，结局为 incomplete。

全程复用已验收的守卫（`scripts/panel_decision/guarded.py`：本任务独占的进程组、GPU 错误即停、一个绝对截止、清理要确认），
只在外面加一层薄的编排：读已有的日志和明细，按预定条件调用守卫已有的有界收尾。不新造通用进程框架，不改公共训练算法，
不碰其他应用的进程。

**V3 用的 64 题**：

- dev16 中分歧的 8 题，按名单列出：
  - exp21:d0165:v0:h16 的 cmp；
  - exp21:d0165:v1:h16 的 readA / readB / cmp；
  - exp21:d0166:v0:h16 的 readA / readB / cmp；
  - exp21:d0166:v1:h16 的 readA。
- 其余 56 题：在 dev16 中排除这 8 题，按 (sample_id, qid) 升序取前 56 题。
- V3 是在 R 上单独做存取（V2 截停时不写 checkpoint），不增加训练后的 checkpoint 验证，也不扩大题量。V2 的训练状态不续训。

**系统 GPU 事件**：

- 时间点：V0 开始时、V1 比较时、V2 截停后、V3 前后、报告时。
- 做法：只读列出 `/Library/Logs/DiagnosticReports` 中新出现的 gpuEvent-*.ips，按文件内的 `timestamp` 字段（不是文件数量，也不是文件名）
  与本次 V 的运行时段对照。
- 时段内有新的 BIF0 page fault 或 MMU interrupt：V 记为 **execution-unverified**，不进入下一步，不进入完整训练。
  如果是在运行中发现、需要停止，只用本任务独占进程组的既有有界收尾，不碰其他应用。
- 这不等于认定本进程是根因，也不据此作废旧权重。

**V 的结局**：只有 V1、V2、V3 都 pass，且整个时段内既没有新的系统 GPU 事件，也没有日志错误，V 才算 pass。即使 pass，也只说明
「这一次 45 分钟的运行在这台设备上没有出错，并与故障前的记录一致」，**不能证明以后的长运行一定安全**。
完整 EXP76 仍然要按第 1 节锁定上限、另行许可，并且全程用守卫。

## 3. 设备选项与边界

- **CUDA**：资源（机器、GPU 型号、可用时间）还没有明确。CUDA 的一致性判据（跨设备不可能逐位一致）等资源明确后再预写；
  上一版提议的 99.5% / 0.02 和「趋势相近」**撤回，不作为通过线**。到时候需要：
  - 用 `uv sync` 按 lock 建环境，记录 torch / CUDA 版本；
  - 用 HF 离线缓存；
  - 拷贝 R 起点和数据，逐个核对 SHA；
  - 配置里只把 `device` 改成 `cuda`，`amp` 仍为 off，TF32 按默认设置并如实记录。
  目前不实现、不运行任何 CUDA 路径，也不升级环境。
- **本机重启**：由负责人执行，或明确批准受控重启。我不自行重启、不关应用、不升级系统或 torch。
- v04-k 两份受影响输出的重测（`docs/experiments/2026-10-20-v04-gpu-evidence-errata.md` 第 3 节）建议也在重启后的 MPS 上做，
  并带一个干净集合作为复现对照。这和 EXP76 是两件事，各自单独申请。
- V 通过后，先回答 R 的普通决策能否学成，再判断是否值得投入后续算力。D1 训练时段（23:55 有系统 GPU 事件）只是一个保留的上游不确定性，
  本方案不从 D1 重训。

## 4. 实现（DEVICE-V-IMPL-PREP-01；只做了 CPU 准备，没有运行）

- `configs/exp76-device-v.yaml`：与 r2 配置相同，只改了 `name`。
- `scripts/device_v/vcheck.py`：纯函数，不起进程、不加载模型。包括：
  - 固定参照（8 个 SHA）和逐题比较（1e-6，预测一致，8 题单列、不豁免；第一次运行只作描述）；
  - 64 题的选取；
  - gpuEvent 按文件内 timestamp 判断（秒级精度，开始那一秒也计入；读不出来、但修改时间落在时段内的文件也计入）；
  - 开机周期；V3 能否开始；V 的唯一结局。
- `scripts/device_v/preflight_v.py`：沿用已验收的 EXP76 检查，另核 8 份参照和开机周期。开机时间仍是 EXP76 故障时那一次（2026-08-07 14:00:43），或不晚于第二次故障结束（04:30:18）时，拒绝运行（exit 12）。
- `scripts/device_v/vrun.py`：复用 `guarded.py` 的 Watch、members、end_group（原文件未改）。
  - 训练进程：每次轮询依次检查 GPU 错误行、系统事件、V1、非有限值、≥ 250 次更新后的 planned_stop、到限。
  - V3：只有 `v3_allowed` 全部满足才启动。
  - 有任何一处清理未确认就退出 71。
- `scripts/device_v/v3.py`（真实模型脚本，从未运行）、`report_v.py`（最后再看一次整个时段内的系统事件，写出实际时长）、`run_v.sh`（只启动一次，只在用户单独许可后手动运行，没有自动接续）。
- CPU 验证：`scripts/device_v/test_device_v.py` 30 项，用假进程和纯数据。真实 MPS 运行、`v3.py` 的真实加载和保存，都没有验证。
