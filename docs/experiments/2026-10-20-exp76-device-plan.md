# EXP76 换设备前的预算重算与最小验证方案（EXP76-TIME-01、GPU-EVIDENCE-PREP-01 C；2026-10-20，只是方案，未运行）

背景：EXP76 两次 MPS 运行都在 d2 中途遇到 InnocentVictim GPU 错误（第一次在 step0 评测中，第二次在第 225–250 步之间），
都已按执行失败收尾（`runs/exp76-panel-decision*/report.json`）。评审裁决不放行第三次原样 MPS 重跑。本文写两件事：
一是按实测重算一次完整运行的时间；二是换设备后在完整训练之前要先过的最小验证。
**训练配方不变**：R 起点、1,054 次更新、数据、seed、精度（amp off）、学习率、监测集合都不动；唯一的变量是设备和运行环境。

## 1. 预算重算（EXP76-TIME-01）

我在第二次运行的回执里写的 ETA 有算术错误：剩余 829 步 × 3.3 s ≈ 46 分钟，从 04:30 算起已到 05:16，再加约 18 分钟终评就是 05:34，
超过了 05:32:09 的停止点。回执里却写成「原本可在停止点前完成」。另外还漏算了一轮评测：`rlcd.py` 在 epoch 末先做一次 `run_eval`，
合并 LoRA 之后又对所有集合重新算一遍 `set_logits`。

一次完整 d2（第二次运行实测，MPS，Apple M4）：

| 部分 | 时间 | 依据 |
|---|---|---|
| 加载 + step0 监测（val、dev16、erased、k_text、4 个 rs_*） | 17.8 分钟 | 实测：阶段 03:59:42 开始，最后一个 step0 文件 04:17:29 |
| 训练 1,054 步 | 55.0–59.2 分钟 | 实测窗口 25–225 步，每步 3.13–3.37 s，按全程不变推算 |
| epoch 末 `run_eval`（同样 8 个集合） | 约 17.5 分钟 | 假设与 step0 的评测部分相同 |
| 合并后的 `set_logits`、拟合温度、写 final 明细 | 约 17.5 分钟 | 假设同上（前向过程相同） |
| 保存，流水线评测 exist（736 题）+ science（577 题） | 约 6.8 分钟 | 10-19 v04-k 上实测 4.3 + 2.0 分钟，另加保存约 0.5 分钟；模型不同，只作估计 |
| report_r2（不加载模型） | < 1 分钟 | 第二次运行实测 3 s |
| **合计** | **约 114–119 分钟** | |

再加上守卫的停止余量（GRACE 15 s + KILL_CHECK 5 s + POLL 2 s + 1 s + 5 s）和报告预留 120 s，总时限至少要约 121–126 分钟。
原来的 5,700 s（95 分钟）**即使没有 GPU 错误也跑不完**：训练大约在第 75 分钟结束，紧接着的 epoch 末评测会被时限截断，结果是「到限、无结论」。

提议（待评审裁决，不自行修改）：时限按换设备后的 V 阶段**实测**各部分时间 × 1.15 重新确定。如果仍是同等速度的 MPS，约为 8,100 s（135 分钟）。
不删监测集合，不复用 step0，不把 epoch 末评测和合并后评测合并成一轮（那要改公共训练实现）。如果要缩短监测，另行提出、另行裁决。

## 2. 换设备后的最小验证（V 阶段，一次性，没有科学结论）

用已经验收的守卫（`scripts/panel_decision/guarded.py`，GPU 错误即停、一个绝对截止、清理要确认）。各步串行，有绝对截止，任一步失败就停下来、
如实记录，不自动重试，也不自动接着跑 EXP76 完整训练。V 阶段通过后，用实测时间按第 1 节重新算时限，再单独申请完整运行。

输入（每次运行前都按 SHA 核对）：

- R 起点 `runs/exp75-panel-r/r`：model.safetensors b7f471fc…、align_report 2721ecd6…；
- 配置与 `configs/exp76-panel-decision-r2.yaml`（fcf044de…）相同，只改 `device`、`name` 和输出路径；
- 数据文件的 SHA 与 EXP76 预检相同。

| 步骤 | 内容 | 通过条件（运行前定下，结果出来后不改） |
|---|---|---|
| V1 读取与评测前向（原第一次故障的路径） | 加载 R（核 SHA），跑完整 step0 监测（8 个集合，3,562 条记录） | 守卫没有发现 GPU 错误，清理已确认。**同一台 Mac 重启后**：与两次 MPS 的 step0 明细逐位一致，dev16 第 992–999 条除外；这 8 条和哪次一致就记哪次，作为第一次运行那批被改变的旁证。**CUDA**：逐位一致不可期待，提议每个集合预测一致率 ≥ 99.5% 且概率最大差 ≤ 0.02（阈值请评审定） |
| V2 反向（原第二次故障的路径） | 同一配置继续训练，在第 100 步后由 V 阶段的时限停下（此时标「到限」是预期的，只作验证用，不产出 checkpoint） | 没有 GPU 错误，清理已确认，loss 有限。Mac 上第 25–100 步的窗口 loss 与第二次运行日志（0.8065 / 0.8454 / 0.7698 / 0.7697）一致；CUDA 上只要求有限且趋势相近（不作为能力证据）。记录每步时间 |
| V3 保存与加载 | 用现有的 checkpoint 读写函数，把 R 存到新目录，重新加载，在 dev16 的固定 64 题上与存之前比较 decide 输出 | 同一设备上逐位一致；文件身份如实记录 |

V2 结束时不会写出 checkpoint，所以 V3 在 R 上单独做。这样不用改训练代码，也不新造保存路径。V1–V3 都不产出科学结论；
即使全部通过，也只说明「这一次短运行没有出错」，**不能证明以后的长运行一定安全**。完整运行仍然用守卫，出错就停。

## 3. 设备选项与边界

- **CUDA**：只有在负责人明确给出资源（机器、GPU 型号、可用时间）之后才准备。到时候需要：
  - 用 `uv sync` 按 lock 建环境，记录 torch / CUDA 版本；
  - 用 HF 离线缓存，或预先下载 laya、siglip2；
  - 拷贝 R 起点和数据，逐个核对 SHA；
  - 配置里只把 `device` 改成 `cuda`，`amp` 仍为 off。CUDA 的 matmul TF32 设置按 torch 默认，并如实记录，不另外修改。
  在资源明确之前不做任何 CUDA 路径的准备。
- **本机重启后的 MPS**：由负责人执行或明确批准受控重启，我不自行重启、不关应用、不升级系统或 torch。重启后、V1 之前只读记录：
  - 开机时间（`sysctl kern.boottime`）；
  - 正在运行的 GPU 密集应用；
  - `/Library/Logs/DiagnosticReports` 下 gpuEvent 文件的数量，作为基线。
  已知限制：系统事件和日志错误并不总是同时出现（见 `docs/experiments/2026-10-20-v04-gpu-evidence-errata.md` 第 4 节），
  所以「没有新的 ips」不能证明没有出错，判断以守卫和逐位对照为准。
- v04-k 两份受影响输出的重测（errata 第 3 节）建议也在重启后的 MPS 上做，并带一个干净集合作为复现对照。这和 EXP76 是两件事，各自单独申请。
