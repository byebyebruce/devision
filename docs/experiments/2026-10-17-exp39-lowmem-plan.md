# exp39 方案：低内存的 512 原图迁移（H 臂重跑；已运行一次，结果见文末：四个投入条件没有全部满足）

日期：2026-10-17。依据：评论家 EXP38-MEM-03、EXP39-PREP-01。

exp38 的 H 臂（512 输入、batch 16）在这台 24 GB 机器上用了约 19.6 GB 的 MPS 驱动内存。与其他应用并存时持续换页，第 350 / 400 步的窗口是每步 27 秒，最终在第 400 步左右按评论家裁决做了有界中断，exp38 记为 incomplete（资源 / 预算原因，不是数值或科学门槛的失败）。C 臂（256）随后单独补救运行（`scripts/exp38/rescue_c.sh`）。

这一份方案只为把 512 的原图迁移在可控内存下重新检验一次：设置与 exp38-H 相同，只改物理执行方式。

## 设置（与 exp38-H 只差执行分块）

- **相同**：起点 exp37-L（sha256 `f9fc93c2…`），用 `scripts/exp38/convert.py` 以 512 读取（只改 config）；数据 exp36 原图 16k（`912a9cd2…`），顺序和 seed 0 相同；全数字遮罩；1,000 个有效更新，有效 batch 16；学习率、LoRA、warmup、44 token、冻结方式都不变。
- **只改**：`micro_batch: 8`。每个有效批的 16 行照常抽取、遮罩、改写数字，然后分两个 8 行的部分前向和反向：
  - 每部分的损失 = 该部分被遮 token 的交叉熵**总和** ÷ 整批 16 行的被遮 token 数，所以两部分的梯度相加，正好等于整批的均值梯度；
  - 每个有效批只做一次 zero_grad、一次 clip、一次 optimizer、一次 scheduler；日志、warmup、eval_every 和 1,000 步都按有效更新计；
  - 每部分在任何更新之前检查有限性，非有限就报错退出，部分梯度不会被用于更新，也不保存 checkpoint；
  - 不保留两部分的计算图。
- **验证**：`align._evaluate` 仍按原来 16 行一批生成说明文字选择、随机遮罩和批内轮转的换图，只把前向切成 8 行，所以题序、换图 id 和分母都不变。
- **数值读出**（`scripts/exp36/readout.py`）：同样先按 16 行生成，再切 8 行前向（这一项要等 C 补救的读出跑完后才改，以免影响正在运行的、已审的读出代码），题单和固定换图映射不变。
- 不和决策监督组合（代码里直接拒绝）。

## 实现与 CPU 验证（df1fb71）

- `src/devision/train/align.py`：`AlignConfig.micro_batch`（默认 0，旧路径完全不变）、`_micro_step`、`_logits_in_parts`。
- `tests/train/test_align_micro.py`（tiny 模型，CPU；按评审 EXP39-R1-01 加强，原版本的验证集其实为空，验证比较 0 次）：
  1. 数据：24 行训练、7 行验证（batch 4，留一个 3 行的尾批，并断言验证集非空）。真实版式的温度 / 磁力数字说明文字（数字的 token 长度不等）和普通说明文字混在一起；数字遮罩（`number_mask_sources`）和分源统计（`track_sources`）都打开。
  2. 整批 4 对 2 × 2：每步损失和步数（12 步）相同；验证真的跑了（第 0、3、6、9、12 步），每次的真图 / 换图准确率和 NLL 都在 1e-5 内相同；最终权重 allclose（1e-5）；逐步记录的分源 token 数、损失份额和准确率都在 1e-5 内相同。
  3. 单独断言第一批里两个半批在数字改写后的被遮 token 数不等，且都大于 0，确认测的是"不等 token 计权"的情况。
  4. 第二部分注入 NaN：在更新前报错，不留 model.safetensors。
  5. 拒绝不整除的 micro_batch 和与决策监督的组合。
- 针对性运行 tests/train/test_align_micro.py 4 项通过，pyright 0 错误（之前一次全量是 223 passed，这次没有重跑全量）。
- "有效 batch 相同"本身不证明更快；等价只说明差别仅在执行分块和浮点误差。

## 资源检查点与失败退出（运行前写定）

- 物理 batch 8 时，激活内存约为原来的一半。原 H 在第 0–250 步稳定在约 17.6–18.6 GB 的 MPS 驱动内存，换页开始前每步约 6.5 秒；8 × 2 的每步时间预计与之相近或略慢（同样的计算量分两次做）。
- **首窗口检查**：第 50 步时读 SwanLab 的 `perf/step_s` 和 `sys/torch_mps_gb`。如果 step_s > 9 秒，或 MPS 驱动内存 > 16 GB 且系统可用内存 < 2 GB，就按 guard 有界结束，记为资源中断，不自动重试，交评论家裁决。
- 之后每个窗口都检查：连续两个训练窗口 > 12 秒 / 步时同样结束。
- 含有 val 的窗口（第 500、1,000 步前后）会被验证耗时拉高，不计入这个规则，单独看 val 耗时（以第 0 步实测为基准）。
- 停滞：若距上一个窗口已超过 50 × 12 秒 = 10 分钟仍没有新窗口（val 期间放宽到 val 基准耗时的 2 倍），也按资源中断结束。
- 完整预算在启动前与评论家一起定。
- 运行前确认没有其他模型进程。是否关闭其他应用由负责人决定，我不会自行关闭。

**读法**（只限这次的设置）：
- 512 让原图上的整数补全比 256 多约 7 个点，速度字段从 0.06 升到 0.17；在"目标值确变的孪生"上第一次出现了区间为正的依图差（+0.075）。
  - 这说明 512 下模型更多地利用了与目标值相关的视觉变化（评论家 EXP39-RESULT-02）。但 real_layout 的孪生图在数值变化时，粒子半径或磁铁间隙也可能跟着变（exp37 已指出的几何线索），所以这不能单独证明模型确实读取了印字。
  - 以上都是 full-number MLM 的读出，不等于 decide 的开放数值识别成绩。
- 但按标签绑定几乎没有改善：异值两对象 H − C +0.007、区间跨 0，速度两对象同时对只有 0.016。投入门槛没过。
  - H 的异值两对象同时对：质量 1/138、速度 3/191、距离 8/85。fit 上约 0.042，所以不只是未见族上的泛化失败。
  - **错误形态**（只读复算 `runs/exp39-h/numbers_tune/numbers.jsonl`，与评论家的数一致）：异值题共有 687 个整数字错误，其中只有 87 个预测 token 串恰好等于另一对象的 gold 串（质量 44/235、速度 17/328、距离 26/124），其余 600 个两个 gold 串都不匹配。同一张图上两对象的预测串相同的有 209/414。
  - 这和 exp25 几乎统一读成另一面板的错误不同，不能只归为 A/B 指向的问题。字形、数字组合 / 格式和绑定可能共同限制了结果。
- 512 的代价很高：对齐末点的保护面板代价更多更重（flip −20.7、count_wide −13.7），CPU 延迟约 2.7 倍。
- 按预写规则，不加长 H，不自动转 B。下一步由评论家决定。
