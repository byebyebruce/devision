# EXP76 r2：一次独立重试的接线（EXP76-RETRY-PREP-01；CPU 准备完成，未运行模型，EXP76-RUN-02 尚未放行）

日期：2026-10-20。worktree `devision-exp76r2`，分支 `exp76-r2-prep`（从 e043088 拉出）。只新增文件；EXP76 原有的配置、预检、runner、报告和公共训练实现都没有改。

## 为什么重试、为什么要加守卫

EXP76 第一次运行在 step 0 遇到明确的 MPS 执行错误（command buffer … InnocentVictim），训练被定向终止，记为 failed / incomplete，没有回答配方是否有效。MLM 短诊断这次没有出现异常，但那不是设备健康的证明。所以重试需要独立的路径，并且要有一个守卫：一旦再次出现同类错误，就立即结束这一组进程，并让这次运行不能形成科学结论。

## 接线

- **配置** `configs/exp76-panel-decision-r2.yaml`：与 `configs/exp76-panel-decision.yaml` 只差 name（因此输出目录是 runs/exp76-panel-decision-r2）。R 起点、数据、1 遍 1,054 次更新、seed、batch / 微批、学习率、冻结范围、监测、探针和 A / B / C / D 规则全部相同；不是续跑；不改 MPS 或精度设置，也不加同步。
- **预检** `scripts/panel_decision/preflight_r2.py`（不加载模型；失败 exit 12，不训练）：
  - 复用已验收的 EXP76 预检全部检查（R 三件、EXP75 证据把 R 记为 completed 且值得、数据 MANIFEST、rlcd 规划 1,054 次），但用 r2 配置和 r2 自己的新路径；
  - 再核对 retry_of 证据都存在且 SHA 不变：第一次的启动标记、d2.log、incomplete 报告、status、out、预检记录、处置记录（before / actions / after / d2.log.before / files.before），以及 MLM 诊断报告；
  - 通过时写 `runs/exp76-panel-decision-r2.START.json`：retry_of（原运行、证据 SHA、原因）以及 r2 配置、脚本、报告、rlcd / pipeline 代码的 SHA。
- **执行守卫** `scripts/panel_decision/guarded.py`：
  - 以独立进程组启动 `uv run devision-pipeline configs/exp76-panel-decision-r2.yaml`；外层 runner 不在这个组里，守卫也从不向 runner 发信号；
  - 把子进程的 stdout / stderr 写入 `runs/exp76-panel-decision-r2-pipeline.out`；
  - 约每 2 s 扫描这个文件和 `runs/exp76-panel-decision-r2/logs/` 下的所有文件（晚创建的文件从头读，只读完整行），子进程结束后再扫最后一次；
  - 看到 "command buffer exited with error status"、"victim of GPU error/recovery"、"kIOGPUCommandBufferCallbackError" 或 "InnocentVictim"，立即记录时间、文件和原文，对该组发 TERM，15 s 后仍存活的成员发 KILL；到达限时同样处理；
  - 组成员由 /bin/ps 列出（排除僵尸进程），因为 macOS 上一旦组里只剩已退出或僵尸成员，os.killpg(pgid, 0) 会返回 EPERM，无法区分组是否还活着。不按名字杀进程。
  - 退出码：自己结束且没有 GPU 错误时，返回子进程自己的退出码；出现 GPU 错误时返回 70（即使子进程返回 0）；到限返回 124。记录写入 `runs/exp76-panel-decision-r2-guard.json`。
- **报告** `scripts/panel_decision/report_r2.py`（不加载模型）：
  - 先判断执行是否有效：守卫记录里有 GPU 错误（包括子进程退出后才扫到的）、到限、或者记录缺失 / 无法读取，都判为执行失败——结局为 "incomplete: execution failed (...) -- no scientific outcome"，没有 A / B / C / D，普通指标只放在 "voided" 下作记录；
  - 执行有效时，结局就是已验收的 d2_report 原样的判定。
  - 报告原子写入 `runs/exp76-panel-decision-r2/report.json`。
- **runner** `scripts/panel_decision/run_r2.sh`：
  - 只启动一次（`runs/exp76-panel-decision-r2.started`）；ps / pgrep 检查后先做预检；
  - 硬上限 5,700 s：守卫的时限 = 截止 − 120 s 报告预留 − 15 s TERM / KILL 宽限，所以宽限算在总预算之内；
  - 守卫结束后，无论退出码如何，都在剩余时间里运行 report_r2；
  - 不重试，不串接任何后续。

## 第 1 轮修正（EXP76-RETRY-R1-01：所有等待都有界）

- 守卫改为接收一个**绝对截止** `--deadline`（runner 传入 运行截止 − 120 s 报告预留 − 5 s）。轮询、TERM 宽限、KILL 之后的检查和所有 child.wait 都按这个截止计算：停止过程最晚在 截止 − 15 s 宽限 − 5 s KILL 检查 − 轮询 − 1 s 时开始，因此会在截止前结束；停止分支里不再有无限的 wait。
- KILL 之后，如果在截止前仍有存活成员或子进程没有被回收，守卫登记剩余的 PID、"child_reaped" 和 "confirmed: false"，写出记录，以 exit 71 返回；不把"发出了 KILL"当成"进程已经退出"。runner 记录 "no further model is started"，之后只运行不加载模型的报告。
- runner 再用 run_capped 在报告预留的边界上限制守卫本身（外层兜底）；报告始终保留完整的 120 s。
- report_r2 的执行有效性改为**只认明确的成功**：守卫记录存在、没有 GPU 错误、退出码为 0、进程组清理已确认。清理未确认（71）、到限（124）、其他非 0 退出、记录缺失，都判执行失败，没有 A / B / C / D，即使磁盘上碰巧有完整的训练和评测文件。

## 运行中的规则（运行前写下）

- 首轮 step0 监测和第一个训练窗口实测后再更新 ETA；不能只凭 CPU 时间低判断死锁。
- 如果再次出现同类 GPU 错误，守卫会结束这一组，这次运行判为 failed / incomplete。之后先停下来收集系统和设备证据，再决定下一条路线，不连续第三次碰运气。
- 预算估计仍是 69–76 分钟，这是在设备健康未经验证的前提下的估计。
