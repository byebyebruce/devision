# exp14：PixMo-Points 计数监督的小规模快速验证

日期：2026-10-12。负责人要求"不自己造数据，用公开数据，先做小规模快速验证"（调研见 `docs/research/image-jev-top10-training-data-2026-10-12.md`）。不算一轮，结论只用来决定是否扩大规模。读法在训练前写下。

## 问题

在同样的训练预算下，用 PixMo-Points 的计数标注替换一部分旧数据回放，能不能提升计数，旧能力会不会受伤？PixMo-Points 的计数部分 v12 没有训练过：v12 构建扩展数据时它因为没下载完被跳过，见 `data/ext/MIX.json` 的 `missing`。

## 设计

| 组 | 训练数据（各 16,000 题，从 v12 起步，2,000 步） |
|---|---|
| A `exp14-base` | 只用 v12 训练池回放：存在性 3,000（每个类别内是 / 否数量相等）、计数 3,000（原格式）、科学 2,000、通用 3,000、v12 扩展 5,000（每个来源 500） |
| B `exp14-pixmo` | A 的每块各取前 75%（是 A 的嵌套子集，共 12,000），加 PixMo-Points 4,000 题：计数 3,000（答案 4–10，一半用 0..10 完整候选，一半用 3–5 个连续数字、正确答案的位置均匀随机）、存在性 1,000（"Are there any <短语> in the image?"，是 = 数量 > 0，否 = 标注者标为数量 0） |

- PixMo 图片取 r13 的 pixmo_two_kind 用过的那批（r13 时已和所有 dev / test / bench 图片隔离；v12 没见过）。按 SHA-256 九比一分成训练和开发面板。
- 开发面板：
  - `px_wide` / `px_narrow`：同 400 题，分别用两种候选格式；
  - `px_exist`：300 题，是否各半。
- 只看选项的规则在窄候选面板上接近随机（下中位数 25.0%，随机 25.8%）。完整候选面板上，最常见答案"4"占 20.5%，这就是只看选项的最好基线。
- 学习率和 v12 重训方案相同（2e-5 / 1e-5 / 5e-5），warmup 100，余弦衰减到 0，seed 0，两组只有数据不同。数据：`scripts/exp14/build.py` → `data/exp14/`（MANIFEST 有分布和规则基线）。
- 比较：第 2,000 步的逐题结果（温度 1），B − A，按图配对 bootstrap 2,000 次（`compare.paired_metric`）。

## 读法（训练前写下）

1. **PixMo 计数有没有学到**：`px_wide`、`px_narrow` 上 B − A 的区间下界 > 0，且 B 在 `px_wide` 上高于最常见答案基线（20.5%）。两项都满足才算"在 PixMo 图上学到了"。
2. **能不能迁移到别的照片**：VQAv2 照片计数 `count_narrow` / `count_wide` 的 B − A，只报告。下界 > 0 才说"有迁移"。
3. **旧能力代价**：存在性平衡准确率、科学、真实照片绑定、`dev_ext` 按 13 个来源等权，B − A 的下界都 > −2 才说"没测到损伤"。哪一项下界 ≤ −2，就如实写出这一项。
4. CountBench 是测试集，不参与这次判断。

结果：1、3 都满足，才建议在 v12 重训配方里加入 PixMo 计数并扩大规模；1 不满足，就说明这份数据在本预算下没用；3 不满足，扩大前先加大回放。

## 结果（2026-10-12 15:25，第 2,000 步，温度 1，B − A，按图配对 bootstrap 2,000 次）

两组都跑满 2,000 步。A 在第 604 步遇到一次 MPS 返回 NaN，从第 500 步续训后越过该步，同一批数据第二次没有再出 NaN，判断为设备偶发故障。数字由 `scripts/exp14/report.py` 算出，保存在 `runs/exp14-pixmo/compare_base.json`。

**按事先写的读法：**

1. **PixMo 计数学到了没有：未满足。** 窄候选显著提高，但完整候选没有提高，B（15.3%）也没超过只看选项的最好基线（最常见答案"4"占 20.5%），规则要求两者都满足。完整候选的 NLL 大幅下降，说明概率分布向正确答案附近移动了，但最高项还没对准。
2. **迁移：分化。** VQAv2 照片原格式计数 +3.3，下界 > 0，**有迁移**；完整候选格式 −11.7，**明显变差**。原因可以从预测分布看出：B 在 VQAv2 完整候选题上最常答 6 / 4 / 5（120 / 90 / 52 次），而这些题的正确答案大多是 1–3。PixMo-Points 计数部分的答案只有 0 或 ≥4，没有 1–3（数据卡写明），完整候选训练把模型的数量先验推向了 4–10。这是候选解释，没有单变量对照。
3. **旧能力代价：没测到损伤。** 存在性、科学、绑定、v12 扩展的下界都 > −2；存在性平衡准确率还略有提高。

**结论**：按读法，"在 PixMo 图上学到计数"不成立，不建议照现在的格式扩大。可以保留的有三项：PixMo 存在性题（+5.3）、窄候选计数（+7.3，且迁移到 VQAv2 原格式 +3.3），以及旧能力无损。完整候选格式会把 1–3 的题答成更大的数，所以 PixMo 只能用窄候选；完整候选的计数监督要换成答案覆盖 0–10 的来源（TallyQA / VizWiz / Objects365 计数），或者按数量重新配平后再试。

**附带发现**：`data/r13b/val.jsonl` 里 242 道 VQAv2 计数题以同一个 id 出现两次（`dev_mix` 的原格式一次，`dev_count_existing` 改写的 0..10 格式一次）。不影响 r13b 的判定，因为 val 只用来拟合温度、作报告，但温度拟合时这些题会被计两次。下次构建时改为给改写的题换新 id。
