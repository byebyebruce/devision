# exp20 方案：视觉 token 从 64 加到 256 的 2,000 步小对照（待评审）

日期：2026-10-15。负责人："准备下一次实验，让评论家审核，他告诉你结果你进行下一步动作"。不算一轮，不产出可采用的模型；评审没有问题再运行。

## 要回答的一个问题

v0.3（r15）还没补上的主要短板：
- 必须看图的自然科学题：49.5% 对 laya-vision 的 70.0%；
- 计数绝对值仍低：CountBench 35.6%；
- 小字和示意图上的"找两处比较"。

`docs/experiments/2026-09-30-rlcd-plateau.md` 的推论是，这类题需要更多视觉 token 或别的结构改变，而不是更多同类样本。之前 v9b 上试过 512 输入（仍是 64 个 token），投影层只对齐了 621 步，比较不公平，所以"分辨率 / token 数不是限制"并没有被排除。

这里问的是：**同一份数据、同一批序、同样 2,000 步，把每张图的视觉 token 从 64 个（2×2 合并）换成 256 个（不合并），看细节类面板会不会比 64 个 token 时更好、其他面板有没有明显损失，CPU 延迟又增加多少？**

## 设计：两组只差一个变量

| 组 | 说明 | 来源 |
|---|---|---|
| A（64 个 token） | 从 r15 接着训，`data/post-r15-order/a.jsonl`（8,000 道题各两次，共 16,000 题次），种子 1，2,000 步 | **复用** Codex 的 `runs/post-r15-order-a`（10-15 00:25 开训，提交 `85ab11d`） |
| D（256 个 token） | 同 A，只把起点换成"r15 + 折叠后的投影层、`visual_shuffle = 1`" | 新训，`configs/exp20-tokens256.yaml` |

- **配置**：`configs/exp20-tokens256.yaml` 的 `stages` 与 `configs/post-r15-order-a.yaml` 只差 `init` 一行（已 diff）。学习率 1e-5 / 5e-6 / 2e-5，warmup 100，micro batch 8，视觉塔不训练，监测面板相同（ext、science、exist、flip、count_wide、count_narrow 和两个倒序计数面板）。
- **数据**：`data/post-r15-order/a.jsonl` 的 sha256 `595bcdb6…`，与 A 开训时冻结的哈希（`runs/post-r15-order/frozen.json`）相同。这份数据里有科学题 1,600、VSR 2,400、镜像 800、计数 3,200 题次。
- **折叠初始化**（`scripts/exp20/fold.py`）：
  - 原投影层把 2×2 共 4 个 patch 拼成 3,072 维，经过 LayerNorm(3072) 和第一层线性层。
  - 新投影层输入单个 patch（768 维）：LayerNorm 的仿射参数取 1 和 0，第一层权重取 W' = Σ_k W_k·diag(γ_k)，偏置取 c' = c + Σ_k W_k·β_k；其余权重和温度都不变。
  - 这样，只要一个 2×2 邻域内的 4 个 patch 相同，新的 4 个 token 就和原来的 1 个 token 完全相同。真实照片的邻域并不完全一样，所以起点会有差别；这个差别用 D 第 0 步对 r15 的读数报告出来。
- **随机数和批序**：折叠在训练之外完成，不消耗训练中的随机数。批序只由数据和种子决定。RLCD 噪声的形状只和选项数有关，与 token 数无关，所以两组的噪声抽样序列相同。
- **CPU 延迟**（结构改了，按 CLAUDE.md 要实测）：在 v0.3 用过的 200 题夹具 `data/r12/cpu_latency.jsonl` 上，用 4 线程、每次请求一题，依次测 r15 和折叠后的起点。延迟只取决于 token 数，和权重无关，所以起点可以代表训练后的 D。
- **长度**：256 + 1 + 文字（最长约 151）≈ 408，小于 `max_len` 512。ModernBERT 的局部注意力窗口是 128，D 中选项位置在局部层看不到大部分视觉 token，只能靠全局层。这是结构本身的一部分，不另做处理。

## 判定（开训前写下，结果出来后不改）

只在第 2,000 步读一次，温度 1 的逐题记录，D − A，逐题配对。重采样单位是图片，镜像图和原图算同一张。

- **P1 细节面板**：`science`、`count_wide`、`count_narrow`、`flip` 四个面板准确率差的等权平均，下界 > 0。
- **P2 不明显伤害**：`exist`、`ext`、`count_wide_reverse`、`count_narrow_reverse` 中，没有任何一个准确率差 ≤ −3 个百分点且上界 < 0。

| 结果 | 条件 | 下一步 |
|---|---|---|
| **有效** | P1 下界 > 0，且 P2 成立 | 结合实测的 CPU 延迟，交负责人决定是否做正式一轮（更长训练、全量评测、采用规则那时另写） |
| **无效** | P1 点估计 ≤ 0 | 不再按这种方式加 token |
| **不确定** | 其他情况 | 交负责人决定 |

只报告的项：
- D 第 0 步对 r15 的 8 面板准确率等权平均，即折叠的起步代价；
- 8 面板 NLL 等权平均（D − A）；
- 每个面板的准确率和 NLL，D − A、D − r15 各一份；
- CPU 延迟 P50 / P95（r15 对 256 token）。

**已知限制**：
- A 本身在温度 1 下 NLL 明显上升（Codex 的结果）。D 和 A 都从 r15 接着训，比较是相对 A 的，这部分影响大致抵消，但 NLL 只作报告。
- `science` 面板不能单独切出必须看图的题；计数面板只有 300 题。
- 单种子、2,000 步，不代表训满的结果；不碰测试集。
- 投影层没有单独对齐，只靠 2,000 步的阶段 2 训练适应 256 个 token。如果判为无效，也只说明"这个预算下的折叠初始化没起效"，不说明 256 个 token 没用。

## 预算

- D 未实测。序列从约 170 个 token 增加到约 360 个，估计每步约 2–2.5 秒（A 是 1.28–1.37 秒），2,000 步加 3 次监测约 1.5–2 小时。
