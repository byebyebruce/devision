  - 紧目标 = 墨迹外接矩形外扩 2 px（与 EXP60 oracle 框同一规则）。在训练图上它是由绘制文字得到的标签，不来自任何开发答案。
- **结果**（中位数，括号内为 p05–p95）：

|---|---|---|---|---|---|---|---|---|
| 训练（train_V / train_P / fit_O） | 992 | 1.00 | 1.00 | 1.00 | 0.06（0.03–0.14） | 0.58 | 140 → 84 | 0.66 |

- **解读**：
  - 竖直方向，真实速度行全部落在 c92 框上下各扩 0.5 个框高的窗口内，所以一个只在窗口里找字的局部校正器是可行的；
  - 横向：dev24 的文字在左边伸出 c92 框约 1.5 px、右边约 3.9 px（中位数），所以校正器的输出也要能调整 x；
  - 训练图上 c92 几乎总是对的（dy 的 p95 只有 0.14），直接用这些框训练，校正器看不到需要校正的偏移，必须对输入框做事先固定的抖动增强；
  - 紧框的 S 包和 c92 的差别很大（dev24 的 Jaccard 0.40）。EXP64 头是在 c92 的包上训练的；它在 dev24 上读紧包是 24 / 24（EXP67 OA / OO），但在生成图上读紧包从没测过，所以运行时要加一个「生成图上的目标区域对照」（紧框，只作描述，不是严格的准确率上界）。不能把「框更贴字」当作必然更好。

## 最小实现（方案通过后再写 runner）

- **触发**：只在速度模板（"What is the average particle speed in sample A / B?"）上触发，按模板文字判断，不看图片 id。质量 / 距离直接用 c92 框，读数应与 c92 路径逐字节相同（运行时核对）。
- **窗口**：c92 框竖直方向上下各扩 0.5 个框高，水平方向左右各扩 8 px，裁到画布内。
- **输入**：
  - 窗口内局部视图（n12 / 0.25 的 12 个视图）的 token，就是视觉编码的 kv[256:] 中与窗口相交的格子（region 的规则），加上它们相对窗口的绝对几何；
  - 问题词向量，与选择器相同（冻结的 ModernBERT 输入嵌入）。
- **输出**：窗口坐标里的一个框 (cx, cy, w, h)，经 pixel_box 换算后交给 region() 和冻结的 EXP64 头。
- **模块**：结构与 c92 的 Selector 相同（问题自注意、一个框 query、两次看图注意、MLP），只给图像注意力加 key padding mask 以支持可变 token 数；从 c92 的权重初始化（维度相同）。约 1.86 M 参数。
- **标签**：只来自训练图（train_V / train_P / fit_O 的速度字段，共 992 个）的紧目标（绘制文字的墨迹外扩 2 px）。
- **增强**（运行前固定，不按开发结果调）：每个训练记录以 seed 0 抽 8 个输入框——c92 框竖直平移 U(−0.5, +0.5) 个框高、水平平移 U(−8, +8) px。范围由窗口定义决定（窗口 ±0.5 h 正好包住这些平移），没有用 dev24 的偏移来定。
- **训练**：CPU；L1 + (1 − GIoU)；AdamW 1e-3、wd 0.01；batch 64；1,000 步、100 步预热后 cosine；seed 0；取末步。
- **特征**：训练图里含速度字段的约 500 张，每张做一次视觉编码（与 EXP64 features 相同），窗口 token 用 float16 写盘。

## 评测与预写门槛（冻结 EXP64 头）

- **读数**：每张图编码一次。
  - rl_tune（600）、tune_V（600）：c92 路径（AA，必须复现 EXP64）、校正路径、目标区域对照（紧框；只描述，不是严格上界）；
  - dev24（24）：c92、校正。dev24 的 oracle 对照不在本轮计算，引用已冻结的外部证据：EXP64 dev24_oracle_new 和 EXP67 OO，都是同一个 EXP64 头（评审 EXP69-NOTE-03）。
- **门槛**：
  - 旧版式 rl_tune 与 EXP61 版式 tune_V：校正路径的速度 exact 和整体 exact 相对 c92 下降 ≤ 0.03；
  - 质量 / 距离的读数与 c92 路径逐字节相同；
  - dev24：速度 ≥ 18 / 24，且相对 c92（16 / 24）的配对差下界 > 0（12 张图重抽）；距离保持 21 / 24（由构造保证，照样核对）。
  - 另报：校正框装下紧目标的比例和 IoU（生成开发切片）。dev24 不当作独立确认。
  - 缺项给 incomplete；失败不加步数、不扫抖动范围。
- **预算**：特征约 3 分钟，训练约 2 分钟，读数约 7–8 分钟（1,224 张图），合计约 15 分钟；建议硬上限 30 分钟，最后 120 秒报告。与其他模型任务串行。

## 风险与边界

- 训练图上的偏移靠人为抖动得到，未必代表真实图的偏移方式（比如 dev24 的框是系统性偏上）。
- 真实字体、JPEG 压缩、贴边文字都没有在训练中出现。
- 生成图上的紧包读数未知，可能比 c92 包差（如同距离字段那样），这是首要的阴性风险。
- 本文件只是设计和审计，不是运行许可。

## 窗口可达性的更正（评审 EXP69-NOTE-01 / 02）

- 上表的「竖直窗 ±0.5 h 内」只说明竖直方向。按最终窗口（上下各 0.5 h、左右各 8 px、裁到画布）计算，紧目标被二维完整包含的比例：
  - train 992 / 992，rl_tune 600 / 600；
  - tune_V 584 / 600（横向 594，竖直 590）；
  - dev24 13 / 24（横向 13，竖直 24）；11 个速度 B 框的紧目标右边超出窗口 0.135–2.770 px。
  - 所以不能写成「全部目标都在窗口里」。
- 评审独立核算：把这 24 个紧目标裁到既定窗口后，dev24 的 S 包（index / 顺序 / rel）全部不变。几像素的越界不等于切掉数字，因此窗口保持不变、不扩大、不重扫。连续 geom 的变化要看实际读数，不预先承诺。
- 「目标区域对照」不是严格的准确率上界；框的 IoU 不能证明读数改善，不新增 IoU 门槛。

- **数据**（`scripts/exp69/build.py` → `data/exp69/`，MANIFEST 记录各项哈希；只用绑定的审计 a94f8f35… 和 data/exp64/train.jsonl）：

- **runner**（`scripts/exp69/exp69.py`、`run.sh`，硬上限 30 分钟，最后 120 秒报告）：
